## 1. 目的と現在の扱い

Judgeが不正JSONを返した場合、判定内容を勝手に加工する代わりに、形式エラーを伝えて最大1回だけ再生成する案を保留・再利用候補として残す。採用は未決定で、今回の作業は本記録のみ。

Gemmaの閉じ角括弧欠落が発端。ただし、推論不能や予算不足まで解決する案ではない。現在の不具合修復を優先し、必要ならその後に限定比較する。Phaseの順序・完了条件は変更せず、MVPの必須追加機能にもしない。

## 2. 試す場合の境界

- 初回成功には追加呼出しを入れず、JSON形式不正の場合だけ追加1回まで。同じ文字列の再解析ではなく、モデルへ再生成を依頼する。
- Provider、判定基準、元回答、参照情報を固定する。「acceptになるまで」判定を取り直さない。元回答を直すRepairとは別の処理として扱う。
- 現行の厳密なDecoderを維持する。引用符置換・文字削除・都合のよいJSONだけの抽出で、不正出力を成功扱いにしない。
- 初回と再試行を合計Token・時間・呼出し回数の予算に含める。Cancel／予算切れでは呼ばず、Load失敗や任意の例外を一律リトライしない。上限変更が必要なら別途判断する。
- 初回失敗と再試行結果を区別して記録し、再試行失敗はunknown／失敗のまま残す。

## 3. 採否の判断

リトライなし／ありを同条件で比較し、JSON解析成功だけでなく、必要な判定基準が揃った利用可能な結果へ回復したかを確認する。

- 試行数・回復件数、最終回答までの所要時間、追加Token・呼出し数を記録する。小標本の結果を一般化しない。
- 回復が少ない、待ち時間の増加が見合わない、停止・予算管理・判定の厳密さが悪化する場合は採用しない。採用のためだけに無制限反復や予算拡大をしない。
- Gemmaでは注意文追加後も同じ不正出力が観測されており、同一Promptの単純反復が有効とは限らない。成功率や許容待ち時間の具体的な基準は、比較に着手する際に定める。

## 4. 見送り時も残す材料

今回のJudge用途で不採用でも、試した条件・回復の有無・遅延とToken費用・失敗理由を残す。将来、別モデルや別の構造化出力処理で再検討できる候補とする。再利用先・時期は未定であり、汎用リトライ基盤の先行実装はしない。

結果が出た際は新規の追記記録から本予約へ連結する。未試行を失敗実績とせず、不採用を技術そのものの無価値とも断定しない。
